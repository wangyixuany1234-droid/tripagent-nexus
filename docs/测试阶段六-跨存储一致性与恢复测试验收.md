## 2. 一致性模型

本阶段确认的权威边界和确定性规则如下：

1. PostgreSQL 是任务、计划、Inbox、Outbox、Agent Result 和审计记录的权威源。
2. Redis 只保存可丢失运行时投影；缓存缺失时从 PostgreSQL 读取并重建。
3. Kafka 采用至少一次投递；消费者以 `(consumer_name, event_id)` Inbox
   唯一约束实现业务幂等。
4. 业务状态和待发送事件使用 Transactional Outbox；发布器以
   `FOR UPDATE SKIP LOCKED` 锁定批次。
5. Outbox 的 `(topic, idempotency_key)` 由唯一索引和 PostgreSQL advisory
   transaction lock 共同保护。
6. Agent Result 以 `result_version` 单调更新，以 `source_event_id` 去重，
   并使用 JPA `@Version` 处理并发写入。
7. 同 Agent 的当前结果按数据库生成的 `execution_sequence` 选择，不依赖
   无序集合或到达时间。
8. 取消、完成和失败竞争采用“首个持久化终态获胜”；任何迟到操作均不能把
   READY/CANCELLED 等终态改回其他状态。
9. 每条任务状态事件持久化 `trace_id`、`source_event_id` 和
   `source_event_type`。
10. Dead Letter 重放生成新 taskId 和 eventId，保留原 causationId，并记录
    replay reason、次数和时间。

## 4. 修复内容

### 4.1 数据库与事件模型

- 新增 Flyway V10：
  - `task_event` 增加 trace 和来源事件字段；
  - `agent_result` 增加结果版本、来源事件、完成时间、乐观锁版本和执行序号；
  - `event_outbox(topic, idempotency_key)` 增加唯一索引。
- Outbox 入队前获取基于 topic 和 idempotency key 的 advisory transaction
  lock；并发重复请求返回已存在的 eventId。
- Outbox 发布批次使用 `FOR UPDATE SKIP LOCKED`，避免多个发布器重复争用同一行。
- Agent Result 拒绝非正版本和非终态结果；重复或旧版本为 no-op。

### 4.2 状态机与恢复

- `EventCausationContext` 同时传递 eventId、eventType 和 traceId。
- `TaskApplicationService` 将来源事件依据持久化到每次状态变化。
- `TaskRecoveryService` 在重启时核对任务的 `result_resource_ids`：
  - 计划已完成则收敛任务；
  - 没有可靠完成依据时不重复危险副作用，转为明确失败。
- `TravelPlanEntity` 的 ready、partial、cancel 和 failed 变更均受终态门禁保护。
- 取消与完成竞争返回明确冲突，不允许任务与计划形成分裂终态。

### 4.3 检索降级

- Neo4j 和 LanceDB 每个路由独立捕获依赖错误。
- 单一路由失败时返回另一条路由的真实证据并记录 warning。
- 所有持久化路由均失败时返回依赖不可用，不生成或伪造来源。

### 4.4 一致性检查器

- 新增只读 SQL 和执行器，支持本地数据库或显式授权的远程测试环境。
- 阈值集中在 `qa/config/consistency-thresholds.json`。
- 输出 JSON 包含检查明细、违规样本、尝试次数和收敛毫秒数。
- 修复了“查询在截止时间后才返回零违规仍被判定通过”的缺陷；现在只有在
  `elapsed <= timeout` 时才算收敛。

## 8. 失败历史与修复复测

1. 任务事件最初沿用任务创建 traceId，不能证明 Kafka 事件因果关系。
   修复来源 trace 传递和持久化后，聚焦测试通过。
2. Agent Result 缺少单调版本，旧结果可能覆盖新结果。增加版本、来源事件
   唯一索引和乐观锁后复测通过。
3. 计划的迟到失败原可覆盖 READY/CANCELLED。增加终态 no-op 门禁，并以两个
   竞争方向复测通过。
4. 首次 Java 全量为 172 项中 1 failure、1 error：
   - 新错误码未进入中文错误码文档；
   - 旧测试尝试把已取消计划改回 READY。
   修复文档和测试数据隔离后，全量 172 项通过。
5. 一致性 SQL 首次聚焦执行使用了错误工作目录。改为同时支持仓库根目录和
   Maven 模块目录后，实际 PostgreSQL V10 执行通过。
6. 独立扫描首次因容器内 `psql` 无法读取宿主机 SQL 路径而失败。修正临时
   执行适配后重新扫描通过，交付脚本本身未绕过。
7. 收敛检查器曾把截止时间后返回的零违规误判为通过。修复时间判定并增加
   回归测试后，超时结果正确失败；最终真实实验在 29.448 秒内通过。
8. Python 全局分支覆盖率首次为 69.89%，补充双检索依赖故障测试后达到
   70.17%。
9. Python 覆盖率门禁曾把 statements 和 branches 的综合比率标为行覆盖率。
   改为读取 line-only 的 `percent_statements_covered`，并增加指标口径回归测试。
10. Redis 场景最初只断言 PostgreSQL 仍可读取。最终增加
    `RedisRuntimeStateService.cacheTask` spy 断言，确认权威读取后确实触发缓存
    重建；聚焦集成测试 11/11 通过。
