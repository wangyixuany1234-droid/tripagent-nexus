# 测试阶段七：故障注入与恢复验收

## 结论

**部分验收，不能视为完整韧性验收通过。**

截至 2026-09-13，40 个要求场景均已执行对应的限定范围实验，最终实验
断言通过。另执行真实 Neo4j 网络故障和真实应用进程重启联动。
“40/40”不是 40 个全链路端到端实验，具体层级见下表。

后续已补齐 `AGENTS_RUNNING` 阶段的串行/并行 Agent 续跑并实际杀进程复测，
见 [Agent 中间步骤续跑补充验收](测试阶段七-Agent中间步骤续跑补充验收.md)。
本报告下方记录为补充开发前的基线，原始结果不改写。

仍未满足的完整验收条件：

- 续跑仅限尚未写入候选计划的阶段；不覆盖任意计划写入中断及非幂等外部副作用。
- 并非每个实验都有可导出的分布式 Trace。部分只有真实任务 traceId、
  HTTP 关联头或测试 Span；未完成逐实验 Jaeger 查询与失败组件定位验收。
- 已验证接口与组件的错误、降级状态，但本阶段没有运行浏览器错误展示验收。
- 连接池、调用并发许可和 Kafka Lag 已分别验证恢复；没有以完整长稳负载
  验证所有服务的线程数、HTTP 连接数和进程内存回到基线。

## 环境与安全边界

- 本地独立 Colima/Lima 虚拟机，x86_64 QEMU 软件模拟；不是生产容量环境。
- PostgreSQL 17.11、Redis 7.4、Kafka native 3.9.1、
  Toxiproxy 2.12.0、Neo4j 5.26，以及隔离目录中的真实 LanceDB。
- 应用使用 Java 21、Spring Boot 测试配置、MockModelGateway、Mock MCP
  供应商；HTTP 异常使用本地 WireMock。没有调用第三方模型或工具。
- 数据为合成旅行、任务、订单和检索 fixture。报告不记录 Prompt、图片或
  Authorization；实验失败保留异常类型、关联标识与日志位置。
- 测试入口检查 Docker 目标，远端需显式授权；真实模型开关强制关闭。
- 默认 Docker context、用户 SSH 配置未修改。虚拟机配置和工具均置于工作区。

## 实验矩阵

| 范围 | 场景 | 注入及实际验证层级 | 最终结果 |
| --- | --- | --- | --- |
| PostgreSQL | 500ms、2s 延迟、断连、池耗尽、重启 | Toxiproxy、占满 Hikari、停止并启动真实数据库；通过 TaskApplicationService 读持久化任务并验证池恢复 | 5/5 |
| Redis | 延迟、断连、清缓存、锁过期 | Toxiproxy、真实 FLUSHDB、真实 TTL；PostgreSQL 状态可读、缓存重建、旧持有者不能删除新锁 | 4/4 |
| Kafka | Broker 不可用、延迟、重复、暂停消费、积压 | 真实 Broker pause/unpause、真实消费者 pause/resume；消息与已提交 offset 的 Lag 核对 | 5/5 |
| Neo4j/LanceDB | 图超时、向量失败、部分结果、无索引 | FastAPI TestClient、真实 LanceDB、图方法注入；实际删除 FTS 索引；另有真实 Bolt 网络实验 | 4/4 |
| FastAPI | 拒绝连接、500、429、超时、非法 JSON、语义缺失 | 真实 Java multipart HTTP 客户端调用本地 WireMock；分类、有限调用、恢复、traceparent | 6/6 |
| 模型 | 超时、限流、5xx、非法结构、极长、空响应 | 生产执行器与结构化输出校验器，供应商为进程内 Stub；校验重试、唯一修复及并发许可 | 6/6 |
| MCP | 地图超时、天气失败、汇率过期、路线不可达、Schema 不符 | Agent 边界 Stub 加官方 MCP 客户端/服务端 HTTP 通道；故障注入供应商目录 | 5/5 |
| A2A | 无响应、FAILED、重复、未登记身份、重启 | SDK handler 异常、真实空注册表、真实 PostgreSQL 版本化回调、恢复服务重建；另有进程重启实验 | 5/5 |

补充实验：

- `retrieval.graphNetwork`：真实 Neo4j 经 Toxiproxy Bolt 下行延迟；
  查询到达配置截止后取消，解除故障后读回唯一合成节点。
- `a2a.processRestart`：真实 Spring Boot 进程，包括 Coordinator 和官方 MCP；
  完成一个基线规划，暂停 Broker，接受三个排队规划，强制终止应用进程，
  恢复 Broker 并启动新进程，核对三个任务全部完成、计划存在且无重复版本。
- 另外验证 `null` 解析响应、缺失集合字段、超时工作线程不响应中断、
  熔断 OPEN → HALF_OPEN → CLOSED，以及模型并发许可不提前释放。

Kafka 重复消息实验明确收到两个同键消息，**没有把 Kafka 说成恰好一次投递**。
业务去重由持久化 Inbox、Agent Result 版本等另外验证。Broker 中断后的发送
结果可能不确定，不能将超时响应解释为消息必然未送达。

## 恢复指标

以下是本机单次实验结果，不是 p95、容量或生产 SLA：

| 实验 | 故障期观测 | 故障解除后的恢复 |
| --- | --- | --- |
| PostgreSQL 500ms 延迟 | 应用读取 1050ms，多次协议往返 | 148ms |
| PostgreSQL 2s 延迟 | 应用读取 4034ms，多次协议往返 | 150ms |
| PostgreSQL 断连 | 3072ms 检测并返回失败 | 157ms |
| Hikari 池耗尽 | 配置 500ms，实测 510ms 返回获取连接失败 | 155ms，active=0、pending=0 |
| PostgreSQL 重启 | 1908ms 检测 | 1321ms |
| Redis 延迟/断连/清空 | 数据库任务可读 | 152/137/155ms 重建投影 |
| Redis 锁过期 | 564ms 观测到失效，新锁不被旧 token 删除 | 释放新锁后 5ms 核对 |
| Kafka Broker 不可用 | 4101ms 检测发送失败 | 593ms，最终 Lag=0 |
| Kafka 延迟 | 消息完成耗时 694ms | 最终 Lag=0 |
| Kafka 1000 条积压 | 1000 条、1000 个唯一键 | 84ms 消费及提交恢复，Lag=0 |
| 真实 Neo4j 网络超时 | 275ms 检测 | 7296ms，唯一节点仍存在 |
| 应用进程重启与积压 | 3 个任务持久化排队，进程被强制终止 | 20063ms 完成核对 |

进程重启实验中，已完成任务的 Agent 执行数为 **8 → 8**；排队任务为
**3 → 3 完成**，最终 PENDING Outbox 为 **0**，无重复计划版本。
这证明排队恢复及已完成任务不重跑，不证明同一个运行中任务的每个中间步骤可续跑。

## 发现与修复

1. 外部调用超时在熔断器之外发生，迟到工作线程返回会被计为成功。
   已先复现连续超时不熔断，再把调用截止纳入熔断统计；参数配置化，
   OPEN/容量耗尽不进行无意义内部重试，工作线程保留并发槽直到退出。
2. 模型调用方超时后提前释放并发许可，未退出供应商调用可被绕过并发限制。
   已复现并修复排队、运行、取消之间的许可归属；覆盖不响应中断的供应商。
3. 解析响应缺少集合或为 `null` 时产生空指针，被误归为可重试服务失败。
   已改为明确不可重试的响应校验错误，并覆盖完整外形但空订单的数据。
4. 结构化模型输出没有长度上限。新增 `MODEL_MAX_RESPONSE_CHARS`，
   超限在 JSON 解析及修复前拒绝；非法/空结构最多仅允许一次修复。
5. 图检索未应用既有超时配置。已使用 asyncio 截止并把超时归为图依赖失败，
   允许其他路由的有效证据继续返回。
6. MCP 过期汇率、不可达路线、无效顶层结果可能被当作成功。
   已补 Agent 边界校验和契约字段，失效数据不交付为成功结果；
   非模拟工具提示不再统一标为模拟数据。
7. 共享 Outbox 发布器错误绑定 OCR 消息开关，规划事件可能永久排队。
   已改为任一消息功能启用即启动发布器；真实进程实验复测通过。
8. 默认 Kafka 失联窗口不适合 30 秒恢复预算。配置消费者会话为 10 秒、
   心跳为 3 秒并支持环境覆盖；原恢复门槛未放宽，进程联动复测通过。

这些改变没有放宽业务校验、删除失败断言或调用真实第三方服务。

## 失败记录

- 超时未触发熔断、极长模型输出被接受、模型许可提前释放均保留修复前
  JUnit 失败记录。
- HTTP 第一次测试误用 HTTP/2，WireMock multipart 基线被重置；
  调整到生产客户端使用的 HTTP/1.1 后才开展实际故障断言。
- 原 MCP 边界中汇率、路线与 Schema 三项失败记录保留。
- 无索引 LanceDB 能自行扫描，不能要求一定失败。修正为核对有效来源及
  索引确实不存在；早期来源断言遗漏图来源，也保留失败记录后修正。
- 进程实验第一次因 Outbox 不发布而排队超时，第二次重启后仍超出 30 秒；
  两次日志和 JUnit 均保留，第三次采用修复后的配置通过。
- 早期 PostgreSQL 2 秒延迟实验的墙钟与单调计时不一致；最终重新执行，
  本报告使用最终一致的 4034ms 读取数据，原记录未覆盖。
- 虚拟机附加网络启动超时、DNS 缺失、镜像仓库 502 等环境失败保留日志，
  不计为业务故障实验通过。
- 默认密钥扫描把 `trip-agent-api traceId=...` 误判为通用密钥；另识别出
  现有固定本地测试令牌和脱敏器测试文本。逐项核对后使用
  `qa/config/gitleaks-evidence.toml` 精确豁免追踪字段及这两个固定测试字面量，
  保留默认密钥规则和额外 DeepSeek/Bearer 规则，不排除报告目录，重新扫描通过。
  这不是完整源码安全审计，不替代后续安全验收。

## 证据格式与产物

每次实验使用唯一文件名，保存注入时间、影响范围、首次检测、降级、清除故障、
恢复、丢失/重复任务、用户影响和相关 traceId。没有业务任务或没有导出 Trace
的实验保留 `null` / 空数组及范围解释，不能擅自写成零或伪造 traceId。
并非所有成功容忍的延迟都需要降级，其降级时间允许为空。

主要目录：

- 最终：`output/test-results/20260913T-stage7-final/`
- 初次实验及缺陷复现：`output/test-results/20260911T-stage7-chaos/`
- 机器摘要：`json/stage7-summary.json`
- 逐实验：`experiments/*.json`
- 汇总页面：`html/stage7.html`
- JUnit：`junit/`
- 覆盖率：`coverage/java/`、`coverage/python/`

汇总器按注入层级分别保留最终结果，低层 Stub 的成功不能掩盖官方传输失败。
`--require-complete` 会因为未完成的完整验收项返回非零，不把限定范围通过
包装成整体通过。
