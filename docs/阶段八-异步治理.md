# 阶段八：异步治理与容错

## 完成项

- AsyncAPI 定义规划、订单解析、检索、Agent、审校、完成、失败和死信主题。
- 统一事件信封包含事件版本、`eventId`、因果链、`traceId`、`taskId` 和
  `idempotencyKey`。
- 事件上限为 256 KiB，递归拒绝图片、Authorization、API Key、OCR 原文和
  完整 Prompt 字段。
- 生产规划和订单解析使用 PostgreSQL Outbox 加 Kafka。
- Inbox 以消费者和事件 ID 去重；可重试失败可重新获取，终态事件不重复执行。
- Kafka 使用有界指数退避；生产或消费重试耗尽后持久化死信。
- 受保护接口支持死信列表和重放；重放创建带 `retryOfTaskId` 的新任务。
- Redis 保存任务/会话投影、SSE 热缓存、地点缓存、恢复锁、限流和幂等加速。
- 外部 HTTP 使用超时、断路器、有限重试和并发隔离。
- 启动恢复只重派安全任务，不安全步骤失败为 `TASK_RECOVERY_UNSAFE`。

## 启动

```bash
export ASYNC_OPERATIONS_TOKEN="$(openssl rand -hex 32)"
DOCUMENT_PARSER_MODE=mock \
RETRIEVAL_PROVIDER_MODE=mock \
MCP_PROVIDER_MODE=MOCK \
PLANNING_PROVIDER_MODE=MOCK \
docker compose up --build -d
```

空 Operations Token 会以失败关闭方式禁用死信管理。

## 接口示例

```bash
curl -H "X-Operations-Token: ${ASYNC_OPERATIONS_TOKEN}" \
  'http://localhost:8080/api/v1/operations/dead-letters?status=PENDING'

curl -X POST \
  -H "X-Operations-Token: ${ASYNC_OPERATIONS_TOKEN}" \
  -H 'Idempotency-Key: dead-letter-replay-0001' \
  -H 'Content-Type: application/json' \
  -d '{"reason":"依赖恢复，运维批准重放"}' \
  http://localhost:8080/api/v1/operations/dead-letters/<dead-letter-id>/replay

curl -N \
  -H 'Last-Event-ID: <last-event-id>' \
  http://localhost:8080/api/v1/tasks/<task-id>/events
```

## 验收覆盖

- Kafka 重复投递只执行一次规划。
- 临时解析失败在有限次数内重试成功且不重复文档。
- 重试耗尽后任务、文档和死信状态一致。
- 不安全的陈旧运行任务明确失败。
- SSE 从 `Last-Event-ID` 后继续。
- 死信接口拒绝无效 Operations 凭据。
- 重放创建新任务，原失败任务保持终态。
- 非法事件只产生脱敏死信，不影响无关任务。

## 重试边界

- Kafka：`maxAttempts` 上限 20，最大退避可配置。
- 模型：有限 `maxAttempts`、每次调用超时和并发上限。
- A2A：每个 Agent Card 声明 1 到 3 次尝试和明确超时。
- 自动重规划：最多一次。
- 任务恢复：`maxRecoveryAttempts` 上限 5。

代码中不存在未设置退出条件的重试循环。

## 限制

- A2A 仍在同一 Spring 进程中执行。
- Redis 故障只降低缓存、锁和限流效率，PostgreSQL 事实不会丢失。
- 运行中不可重复步骤不会自动重做，需要人工判断后创建新任务。

## 验收

Outbox、Inbox、死信、恢复、SSE 续传、有限重试和 Redis 降级均有自动化
测试；真实 Kafka/Redis 连通性由阶段十 Testcontainers 覆盖。
